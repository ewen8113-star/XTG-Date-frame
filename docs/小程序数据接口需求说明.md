# 鑫通告小程序数据接口需求说明

> 文档版本：V1.1  
> 更新日期：2026-07-14  
> 用途：说明种子经纪运营结算后台需要从鑫通告小程序服务端读取的数据。

## 1. 对接目的

种子经纪运营结算后台需要读取小程序中的经纪人、通告、报名签约和业务状态数据，用于：

- 查看经纪人及其通告。
- 审核通告是否有效。
- 审核通告是否产生有效签约。
- 判断签约人员是否为本季度首次与该经纪人合作。
- 识别通告取消、举报、下架及经纪人违规情况。
- 计算种子经纪奖励和推荐奖励。

本文只涉及相关数据的读取接口；运营审核、奖励计算、结算和付款不在本次接口需求范围内。

## 2. 接口形式说明

建议提供服务端 JSON 接口。接口地址、接口名称、鉴权方式和具体实现可以沿用小程序现有规范，不要求必须使用本文示例中的路径。

只要能够稳定取得本文所列数据即可。如果部分数据已经包含在现有接口中，可以直接复用，不需要重复开发新接口。

建议接口支持：

- 按更新时间获取新增或发生变化的数据。
- 数据较多时分页返回。
- 根据唯一 ID 查询单条详情。

通用数据格式建议：

- 所有业务 ID 使用字符串返回，避免超长数字精度丢失。
- 时间带完整日期、时间和时区，例如 `2026-07-14T10:30:00+08:00`。
- 未知或没有值的字段返回 `null`，不使用 `"-"` 代替。
- 每条可变数据尽量带 `updatedAt`，便于后台只同步发生变化的数据。

## 3. 需要的接口和数据

### 3.1 经纪人列表/详情

建议接口：

```text
GET /brokers
GET /brokers/{brokerId}
```

接口路径可以按现有系统调整。

需要的字段：

| 字段 | 类型 | 必需 | 说明 |
| --- | --- | --- | --- |
| `brokerId` | string | 是 | 经纪人/小程序用户唯一 ID，需长期保持不变 |
| `nickname` | string | 是 | 昵称 |
| `wechatPhone` | string/null | 否 | 微信授权手机号 |
| `boundPhone` | string/null | 否 | 业务绑定手机号 |
| `realNameStatus` | string | 是 | 未认证、认证中、已认证、认证失败 |
| `accountStatus` | string | 是 | 正常、限制发布、临时封号、永久封号等 |
| `registeredAt` | datetime | 是 | 注册/入驻时间，用于判断入驻季度 |
| `lastLoginAt` | datetime/null | 否 | 最近登录时间 |
| `violationCount` | integer | 是 | 当前有效违规次数，无违规返回 0 |
| `publishedBriefingCount` | integer | 否 | 累计发布通告数，用于数据对账 |
| `completedBriefingCount` | integer | 否 | 累计结束通告数，用于数据对账 |
| `signupRecordCount` | integer | 否 | 累计报名次数 |
| `contractRecordCount` | integer | 否 | 累计签约次数 |
| `signupUserCount` | integer | 否 | 累计去重报名人数 |
| `contractUserCount` | integer | 否 | 累计去重签约人数 |
| `createdAt` | datetime | 否 | 数据创建时间 |
| `updatedAt` | datetime | 是 | 数据最后更新时间 |

### 3.2 通告列表

建议接口：

```text
GET /briefings
```

建议可以按 `brokerId`、发布时间范围和更新时间查询。

需要的字段：

| 字段 | 类型 | 必需 | 说明 |
| --- | --- | --- | --- |
| `briefingId` | string | 是 | 通告唯一 ID，需长期保持不变 |
| `brokerId` | string | 是 | 发布该通告的经纪人 ID |
| `title` | string | 是 | 通告标题 |
| `status` | string | 是 | 当前状态，如报名中、进行中、已结束、已取消、已下架 |
| `publishedAt` | datetime/null | 是 | 实际发布时间 |
| `finishedAt` | datetime/null | 否 | 正常结束时间 |
| `cancelledAt` | datetime/null | 否 | 取消时间 |
| `cancelType` | string/null | 否 | 主动取消、平台取消、举报取消等 |
| `cancelReason` | string/null | 否 | 取消、下架或举报成立原因 |
| `signupRecordCount` | integer | 是 | 报名记录数 |
| `contractRecordCount` | integer | 是 | 签约记录数 |
| `signupUserCount` | integer | 是 | 去重报名人数 |
| `contractUserCount` | integer | 是 | 去重签约人数 |
| `updatedAt` | datetime | 是 | 通告状态或人数最后更新时间 |

### 3.4 报名与签约人员明细

建议接口：

```text
GET /participants
GET /briefings/{briefingId}/participants
```

如果现有接口已经能按通告或经纪人取得全部报名、签约记录，可直接复用。

仅提供报名人数、签约人数或人员姓名不能满足奖励判断，需要每条人员记录带稳定的人员唯一 ID。

需要的字段：

| 字段 | 类型 | 必需 | 说明 |
| --- | --- | --- | --- |
| `participantRecordId` | string | 是 | 本次通告中的报名/签约记录 ID |
| `briefingId` | string | 是 | 通告 ID |
| `brokerId` | string | 是 | 通告发布经纪人 ID |
| `modelUserId` | string | 是 | 报名/签约人员唯一 ID，历史合作判断的主要依据 |
| `displayName` | string | 是 | 人员显示名称 |
| `phone` | string/null | 否 | 手机号，仅用于辅助核对 |
| `gender` | string/null | 否 | 性别 |
| `age` | integer/null | 否 | 年龄 |
| `profileStatus` | string/null | 否 | 主页资料是否完整 |
| `status` | string | 是 | 已报名、待签约、已签约、未通过、已撤回、已解约等 |
| `signedUpAt` | datetime/null | 是 | 报名时间 |
| `contractedAt` | datetime/null | 是 | 签约时间 |
| `cancelledAt` | datetime/null | 否 | 撤回或解约时间 |
| `cancelReason` | string/null | 否 | 撤回或解约原因 |
| `updatedAt` | datetime | 是 | 记录最后更新时间 |

示例：

```json
{
  "participantRecordId": "contract_987654321",
  "briefingId": "1501847771615395840",
  "brokerId": "1503934885240832000",
  "modelUserId": "1340932330631004160",
  "displayName": "Mia",
  "phone": "13800138000",
  "gender": "女",
  "age": 24,
  "profileStatus": "COMPLETE",
  "status": "CONTRACTED",
  "signedUpAt": "2026-07-18T16:20:00+08:00",
  "contractedAt": "2026-07-19T11:05:00+08:00",
  "cancelledAt": null,
  "cancelReason": null,
  "updatedAt": "2026-07-19T11:05:00+08:00"
}
```

后台需要判断签约人员是否为“本季度首次与该经纪人合作”，因此希望能够取得该经纪人的历史签约记录。

判断时主要使用 `modelUserId`，不能只用姓名；手机号可能变化，只作为辅助信息。

### 3.5 报名/签约人员资料

签约者详情希望采用与通告详情相同的获取方式：报名/签约明细先返回签约者唯一 ID，运营后台再通过该 ID 自动获取并保存完整签约者详情。

建议接口：

```text
GET /models/{modelUserId}
```

根据鑫通告现有签约者详情页面，希望同步以下已有信息。现有页面没有值的字段可以返回 `null`，不要求补录。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `modelUserId` | string | 人员唯一 ID |
| `displayName` | string | 显示名称 |
| `wechatId` | string/null | 页面展示的微信号；如接口权限允许则提供 |
| `roleTags` | string[] | 人员身份标签，如模特 |
| `accountStatus` | string | 当前账号状态，如正常、受限等 |
| `registeredAt` | datetime/null | 注册时间 |
| `lastLoginAt` | datetime/null | 最近登录时间 |
| `violationCount` | integer | 违规次数 |
| `acceptedBriefingCount` | integer/null | 接通告数量；现有系统有则提供 |
| `avatarUrl` | string/null | 头像访问地址 |
| `photoUrls` | string[] | 个人主页照片/模卡照片访问地址列表 |
| `photosUpdatedAt` | datetime/null | 照片最后更新时间；现有系统有则提供 |
| `detailUrl` | string/null | 鑫通告原始人员详情页地址；现有系统方便提供时返回 |
| `gender` | string/null | 性别 |
| `age` | integer/null | 年龄 |
| `birthday` | date/null | 生日 |
| `heightCm` | integer/null | 身高；源系统有则提供 |
| `weightKg` | number/null | 体重；源系统有则提供 |
| `region` | string/null | 所在地区 |
| `bustCm` | number/null | 胸围 |
| `waistCm` | number/null | 腰围 |
| `hipCm` | number/null | 臀围 |
| `shoulderWidthCm` | number/null | 肩宽 |
| `shoeSize` | string/null | 鞋码 |
| `clothingSize` | string/null | 衣服尺码 |
| `tattooDescription` | string/null | 纹身情况 |
| `hairColor` | string/null | 发色 |
| `hairLength` | string/null | 发长 |
| `languages` | string[] | 语言 |
| `introduction` | string/null | 文字介绍 |
| `categoryTags` | string[] | 人员类型或可承接岗位标签；源系统有则提供 |
| `profileStatus` | string | 主页资料是否完整 |
| `profileMissingFields` | string[] | 资料不完整时的缺失项；源系统有则提供 |
| `updatedAt` | datetime | 资料最后更新时间 |

如鑫通告现有接口可以提供实名认证状态、违规记录、接通告记录和举报记录，也可以在签约者详情中返回摘要，或沿用现有相关查询接口。其中“接通告记录”可用于核对历史合作；鑫通告当前没有真人照片审核，因此不要求增加真人审核字段或功能。

照片无需逐张人工整理或单独提供。签约者详情接口根据 `modelUserId` 返回该人员现有的头像及照片 URL 列表，并允许运营后台读取。签约者人数较多时，由运营后台按签约者 ID 自动查询。

图片地址和访问方式可以沿用鑫通告现有方案：

- 如果图片可以直接访问，接口返回现有图片 URL 即可。
- 如果图片 URL 有有效期，接口返回当前有效地址，运营后台需要查看时可重新调用详情接口获取。
- 如果图片需要鉴权，请允许运营后台使用接口凭证读取，或提供现有的授权访问方式。

示例：

```json
{
  "modelUserId": "1340932330631004160",
  "displayName": "Mia",
  "wechatId": "example_wechat",
  "roleTags": ["模特"],
  "accountStatus": "NORMAL",
  "registeredAt": "2026-07-07T21:05:00+08:00",
  "lastLoginAt": "2026-07-12T20:40:00+08:00",
  "violationCount": 0,
  "avatarUrl": "https://image.example.com/avatar/1340932330631004160.jpg",
  "photoUrls": [
    "https://image.example.com/model/1340932330631004160/01.jpg",
    "https://image.example.com/model/1340932330631004160/02.jpg"
  ],
  "photosUpdatedAt": "2026-07-14T10:30:00+08:00",
  "detailUrl": "https://example.com/model/1340932330631004160",
  "gender": "女",
  "age": 24,
  "birthday": "2002-01-01",
  "region": "上海市普陀区",
  "heightCm": 168,
  "weightKg": 50,
  "introduction": "个人资料介绍",
  "profileStatus": "COMPLETE",
  "updatedAt": "2026-07-14T10:30:00+08:00"
}
```

照片用于运营人员人工核验签约者资料。鑫通告目前没有真人审核，因此当照片疑似非本人时，运营人员会在本后台将该新增签约判定为无效。本次仅读取现有资料和照片，不新增真人审核需求。

本次范围仅包含现有人员主页中可用于审核的数据及照片访问能力，不新增原本不存在的人员资料字段。

如果现有系统保存了签约时的人员资料快照或资料版本，也希望一并提供；如果没有，先提供当前人员资料即可。

接口接通后的自动获取流程如下：

1. 运营后台同步通告的报名/签约人员明细。
2. 从人员明细中取得每名签约者的 `modelUserId`。
3. 运营后台按 `modelUserId` 自动调用签约者详情接口，取得资料和照片 URL 列表。
4. 运营人员在本后台点击签约者即可查看同步后的详情和照片，不再需要逐人跳转鑫通告页面查询。

上述过程均由运营后台自动完成，接口具备按人员 ID 查询详情和图片访问地址的能力即可。

### 3.6 通告取消、举报和违规信息

如果通告详情及经纪人详情已经包含完整的当前状态、变化时间和原因，可以直接使用现有接口，不一定需要单独新增事件接口。

如果现有状态字段无法反映历史变化，可提供类似以下查询：

```text
GET /business-events
```

需要能够识别的情况：

- 通告由发布者主动取消。
- 通告被平台下架或取消。
- 通告因举报成立被取消。
- 通告恢复或正常结束。
- 签约人员取消签约或解约。
- 经纪人新增违规、撤销违规或账号状态变化。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `eventId` | string | 事件唯一 ID |
| `objectType` | string | 经纪人、通告或签约记录 |
| `objectId` | string | 对应对象 ID |
| `brokerId` | string/null | 关联经纪人 ID |
| `briefingId` | string/null | 关联通告 ID |
| `eventType` | string | 取消、下架、举报成立、违规等事件类型 |
| `reason` | string/null | 原因 |
| `effective` | boolean | 是否已成立并生效 |
| `occurredAt` | datetime | 实际发生时间 |
| `updatedAt` | datetime | 记录最后更新时间 |

### 3.7 推荐关系

如果经纪人邀请、邀请码或上下级关系保存在小程序系统中，希望提供推荐关系数据。

建议接口：

```text
GET /referral-relations
```

需要的字段：

| 字段 | 类型 | 必需 | 说明 |
| --- | --- | --- | --- |
| `relationId` | string | 是 | 关系唯一 ID |
| `referrerId` | string | 是 | 推荐人/上线经纪人 ID |
| `refereeId` | string | 是 | 被推荐人/下线经纪人 ID |
| `boundAt` | datetime | 是 | 绑定生效时间 |
| `status` | string | 是 | 有效、已修正或已失效 |
| `invalidatedAt` | datetime/null | 否 | 失效时间 |
| `invalidReason` | string/null | 否 | 失效或修正原因 |
| `updatedAt` | datetime | 是 | 记录最后更新时间 |

如果推荐关系不在小程序中保存，则该接口不需要提供，由运营后台自行维护。

## 4. 状态值说明

小程序可以继续使用现有状态编码，只需保证同一编码含义稳定，并告知每个编码代表的中文含义。

建议至少可以区分：

### 4.1 实名状态

- 未认证
- 认证中
- 已认证
- 认证失败

### 4.2 账号状态

- 正常
- 限制发布
- 临时封号
- 永久封号

### 4.3 通告状态

- 草稿
- 待审核
- 报名中
- 进行中
- 已结束
- 已取消
- 已下架
- 审核不通过

### 4.4 人员在通告中的状态

- 已报名
- 待签约
- 已签约
- 未通过
- 已撤回
- 已取消签约/已解约

## 5. 分页和增量同步建议

本节只说明接口需要具备的数据查询能力。自动同步频率、手动刷新和异常提示将在接口取得后由运营后台设置，不属于本次接口获取范围。

数据量较多时，希望列表接口支持类似以下参数：

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `cursor` 或 `page` | string/integer | 分页位置 |
| `limit` 或 `pageSize` | integer | 每页数量 |
| `updatedFrom` | datetime | 只返回该时间之后新增或变化的数据 |
| `updatedTo` | datetime | 本轮同步截止时间；现有系统方便支持时提供 |

分页形式可以使用小程序现有规范，不要求特定命名。

后台会按唯一 ID 保存数据，同一条数据重复返回没有问题；关键是新增、状态修改、取消、解约和违规变化能够被同步到。

## 6. 返回结构示例

可以使用小程序现有统一响应结构。以下仅为示例，不要求完全一致：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [],
    "nextCursor": null,
    "hasMore": false
  }
}
```

如果请求失败，希望返回可读的错误信息，便于联调时判断是权限、参数、数据不存在还是服务异常。

## 7. 最重要的几个数据要求

接口路径、分页方式、状态编码和响应外层结构都可以沿用现有系统。以下几项数据需要尽量保证：

1. 经纪人 ID、通告 ID、签约人员 ID 均为长期稳定的唯一 ID。
2. 能取得通告完整详情，而不是页面列表中的截断摘要。
3. 能取得每条报名和签约人员明细，而不只是汇总人数或姓名。
4. 能通过签约人员 ID 查询历史签约，用于判断是否首次合作。
5. 通告取消、举报取消、下架、签约取消和经纪人违规等变化能够被同步。
6. 记录带更新时间，便于后台只读取发生变化的数据。
